# Rodada 2 — Reorganização por Modelo + Correção de Georreferência (mesma data)

## Problemas Identificados

1. Os scripts exploratórios não distinguiam claramente WRF de ERA5 — nomes ambíguos (`explore_wrf_data.py` já sugeria WRF, mas não havia equivalente ERA5)
2. O arquivo `WRF_d02_bigua.nc` **não continha lat/lon reais** — apenas índices de grade (`south_north` 0–785, `east_west` 0–878), perdidos durante processamento com CDO (`mergetime`). Isso impediria o LorenzCycleToolkit de selecionar áreas por graus (`box_limits`).
3. Não havia geração automática do namelist do LEC a partir dos dados explorados.

## Correções Realizadas

### 1. Scripts renomeados/criados com sufixo por modelo
- `inspect_structure_wrf.py` / `inspect_structure_era5.py` (substituem `inspect_wrf_structure.py`)
- `explore_data_wrf.py` / `explore_data_era5.py` (substituem `explore_wrf_data.py`)
- `plot_basic_fields_wrf.py` / `plot_basic_fields_era5.py` (substituem `plot_basic_fields.py` e `plot_basic_fields_v2.py`)
- `track_viewer_era5.py` (substitui `track_viewer.py`, que tentava plotar track real sobre domínio WRF sem lat/lon — logicamente incorreto)
- Figuras antigas (`basic_fields_*.png`) apagadas e regeneradas com prefixo `wrf_`/`era5_`

### 2. Geração automática de namelist para o LorenzCycleToolkit
- Novo utilitário `scripts/utils/namelist_writer.py`
- `inspect_structure_{wrf,era5}.py` geram `../LorenzCycleToolkit/inputs/namelist_{WRF,ERA5}_bigua`
- Suporta tanto `Geopotential` (m²/s², ERA5) quanto `Geopotential Height` (m, WRF — variável `ght`), conforme aceito pelo LEC (`src/utils/box_data.py`, `src/frameworks/lec_moving_framework.py`)

### 3. Correção da georreferência do WRF
- Confirmado (via `ncdump -h`) que `WRF_d02_bigua.nc` não tem nenhuma variável/coordenada lat/lon — apenas índices de grade
- Buscado e não encontrado: arquivos WRF pré-merge, `geo_em.d02`, `wrfout` original, `namelist.wps`/`namelist.input` em todo o filesystem acessível
- Usuário forneceu os arrays reais de lat (786 valores) e lon (879 valores) via Google Drive
- Novo script `scripts/analysis_01_preprocessing/prepare_wrf_for_lec.py`:
  - Seleciona apenas as variáveis necessárias para o LEC: `t`, `ght`, `omega`, `u`, `v`
  - Aplica as coordenadas reais, renomeando `south_north`→`lat`, `east_west`→`lon`
  - Gera `data/WRF_d02_bigua_LEC.nc` (5.3 GB, reduzido de 18.2 GB)
- Coordenadas recuperadas salvas em `data/metadata/wrf_d02_{lat,lon}.json`, com proveniência em `wrf_d02_latlon_download.json`

### 4. Documentação atualizada

# Rodada 3 — Track do WRF + Correção do Erro de `time` no LEC (mesma data)

## Problema 1: Track do ciclone rastreado no WRF

Usuário forneceu `track_vort850_biguaWRF_20260730_170859.csv` (posição bruta e corrigida do centro do ciclone, via mínimo de vorticidade em 850 hPa, calculado diretamente sobre o WRF — 25 pontos, 2024-12-13 12Z a 2024-12-16 12Z, todo o período simulado).

- Salvo como `data/bigua_track_track_WRF.csv`
- Novo script `scripts/exploratory/track_viewer_wrf.py`: plota posição bruta vs. corrigida sobre o domínio WRF → `figures/exploratory/wrf_track_overview.png`
- Novo script `scripts/analysis_01_preprocessing/prepare_track_for_lec.py`: extrai apenas `lat_corrigida`/`lon_corrigida`, converte para o formato exigido pelo LEC (`time;Lat;Lon`, data `YYYY-MM-DD-HHMM`, ver `src/utils/validation.py`) → `data/bigua_track_WRF_LEC.csv`

## Problema 2: Erro ao rodar o LorenzCycleToolkit

Usuário rodou o LEC com `namelist_WRF_bigua` e o track processado, e obteve:
```
numpy._core._exceptions._UFuncNoLoopError: ufunc 'subtract' did not contain a
loop with signature matching types (dtype('<U19'), dtype('<U19')) -> None
```
em `preprocessing.py:186`, ao calcular `data[TimeIndexer][1] - data[TimeIndexer][0]`.

**Causa raiz**: `data/WRF_d02_bigua_LEC.nc` armazenava a coordenada `time` como **string pura** (`string time(time)` no netCDF bruto, herdado de `WRF_d02_bigua.nc`), não como tempo codificado via CF-convention (unidades + calendário). O xarray carregava `time` com `dtype=object` (strings), e o LEC assume `datetime64` para calcular a resolução temporal por subtração.

**Correção**: `prepare_wrf_for_lec.py` agora converte `time` para `datetime64[ns]` (via `pd.to_datetime`) antes de salvar — o xarray grava a codificação CF correta (`hours since 2024-12-13 00:00:00`, `calendar=proleptic_gregorian`) no netCDF de saída. Arquivo `WRF_d02_bigua_LEC.nc` regenerado e validado (a subtração `time[1]-time[0]` foi testada isoladamente e retorna 3.0h corretamente).

**Nota**: o ERA5 (`ERA5_d02_bigua_LCT.nc`) já tinha `time` corretamente codificado desde a origem (double + units + calendar) — este bug afetava apenas o WRF.

## Problema 3: Track ultrapassava o fim dos dados

Segunda tentativa de rodar o LEC falhou com:
```
❌ Track final timestamp is later than data final timestamp!
Data: 2024-12-13T00:00:00 a 2024-12-16T00:00:00
Track: 2024-12-13 12:00:00 a 2024-12-16 12:00:00 ← TOO LATE!
```

**Causa**: os dados WRF começam 12h antes do track (spin-up do modelo, 2024-12-13 00h–09h, sem ponto de track correspondente) e terminam 12h antes do fim do track (2024-12-16 12h não coberto pela simulação).

**Correção** (a pedido do usuário — descartar spin-up inicial e truncar o track no fim da simulação):
- `prepare_wrf_for_lec.py`: agora lê o início do track (`data/bigua_track_track_WRF.csv`) e corta os dados WRF com `ds.sel(time=slice(track_start, None))`, removendo os 4 time steps de spin-up (25→21 steps, início em 2024-12-13 12:00)
- `prepare_track_for_lec.py`: agora lê o fim disponível em `WRF_d02_bigua_LEC.nc` e trunca o track para não ultrapassá-lo (25→21 pontos, fim em 2024-12-16 00:00)
- Validado programaticamente: período do dado e do track agora coincidem exatamente (2024-12-13 12:00 a 2024-12-16 00:00, 21 steps/pontos)
- `namelist_WRF_bigua` e metadados regenerados para refletir o dado cortado
